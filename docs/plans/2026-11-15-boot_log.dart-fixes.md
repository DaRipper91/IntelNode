# lib/boot_log.dart: Fix Plan — 2026-11-15

> **Implement task-by-task, in order.** Task 1 is the priority: make `BootLog` unable to change caller control flow (F1, F4, C1). Today `BootLog.event` sits inside `Util.execute`'s `try`, so any throw from the logger turns a real exit code into `-1` (reproduced in the same shape: exit 0 and 137 both returned -1). The same exposure exists at the `waitForXServer`, `launchXServer`, `Workflow.workflow` and `TermPty` hook sites. The trigger is latent (nothing throws with the default `debugPrint` printer), so this is hardening, but the blast radius is the boot path.

**Context:** `lib/boot_log.dart` (new, untracked) mirrors boot/X-server events and pty output to logcat (`debugPrint`, prefix `IntelNode`) and an optional rolling file. Hook sites are in `lib/workflow.dart`, tests in `test/boot_log_test.dart`. This pass found no blocker; `flutter analyze` on the file is clean and the 13 existing tests pass (suite baseline 106 -> 119 per the requester, analyze 19 pre-existing infos). ANSI/CR reassembly, the flood cap on streamed lines, the file-failure policy and rollover are solid; see "Strengths" before touching them.

**Global rules for every task**
- Source edits only in the files named in each task. Do NOT run `dart format` repo-wide (project forbids it); match existing style by hand.
- Always `--no-pub` for flutter commands. No device/adb needed except Task 3's gate.
- Tasks touching `lib/boot_log.dart` must keep all 13 existing tests passing unchanged (do not edit existing tests to make them pass) and add new tests in `test/boot_log_test.dart`.
- Final gate after every task: `flutter test --no-pub test/boot_log_test.dart` then `flutter analyze --no-pub` (must stay at 19 pre-existing infos, no new ones), and before merge the full `flutter test --no-pub` (expect 119 plus new tests, no failures).
- Rollback for every task: it is a single-file revert of the task's edits (`git` has no history for `boot_log.dart` yet, so commit after each task to make this possible).

## Task 1 — BootLog: isolate logger failures so they can never alter caller control flow (F1, F4, C1)

**Problem:** `event` L73, `feed` L48-64, `flush` L67-70, `_out` L129-132 and the notice in the `_toFile` catch (L146) do not isolate failures of `printer`. Reproduced (r2): a throwing `printer` propagates out of `event`/`feed`/`flush`. In `Util.execute` (workflow.dart L117-124) `BootLog.event` at L119 is inside `try/catch (e) { return -1; }`, so real exit codes 0 and 137 both came back as -1; `executeCapture` (L147-155) would return `(-1, "Error waiting for shell exit...")` and discard captured output; the `TermPty` exit handler (L572-580) would skip `terminal.write`, `SystemNavigator.pop` and `launchSignal9Page` (unhandled Future error). Same exposure, verified by reading only (not reproduced): `waitForXServer` L408/L412/L417 (a throw on the success path aborts boot; at L417 it replaces the `TimeoutException`), `launchXServer` L1901 (skips the X server launch) and L1907 (replaces the original launch error before `rethrow`), `Workflow.workflow` L1919/L1929. Separately (F4, reproduced r3): if `printer` throws midway through emitting a chunk's lines, `_pending[tag]` (assigned only at L63) is not updated, so already-emitted lines are re-emitted on the next feed and the later lines plus the new remainder are lost. Severity: medium (latent trigger, high blast radius).

**Steps:**
1. In `lib/boot_log.dart`, make `_out` (L129-132) call `printer(line)` and `_toFile(line)` each in their own `try { ... } catch (_) { ... }` so a failing printer cannot skip the file write and vice versa. Catch `Object` (not just `Exception`).
2. Make the `printer(...)` call inside the `_toFile` catch (L146) guarded the same way (shared private helper, e.g. `_safePrint(String)`).
3. Do not swallow silently (project error-handling rule): on a caught printer failure, count it in a private `_loggerFailures` int and report the first one through a last-resort `debugPrint` inside its own try/catch (no recursion into `printer`). Keep it to one report per process.
4. In `feed` (L48-64) assign `_pending[tag] = StringBuffer(remainder)` BEFORE emitting any lines (compute `remainder` first, then emit), so state is consistent regardless of emission failures (F4).
5. Wrap the bodies of the public entry points `event`, `feed`, `flush` and `attachFile` in the same guard as a second line of defence (for non-printer faults, e.g. a future edit adding a throwing path). Keep `reset()` unguarded.
6. Do NOT change the `workflow.dart` hook sites for this task; the guarantee belongs in `BootLog`.
7. Add tests to `test/boot_log_test.dart` (new group `BootLog failure isolation`):
   - `printer` that throws: `event`, `feed` (with newline), `flush` do not throw.
   - A throwing printer on line 2 of a 3-line chunk: lines 1 and 3 behaviour is defined and the next `feed` does not re-emit line 1 (F4 regression test).
   - With a file attached and a throwing printer, the line still reaches the file.
   - Throwing printer inside the "file disabled" notice path does not throw.
   - Mirror the `Util.execute` shape in a test: `try { BootLog.event(...); return 0 } catch (_) { return -1 }` returns 0 with a throwing printer.

**Verification:** `flutter test --no-pub test/boot_log_test.dart` (13 existing + new tests green), then `flutter analyze --no-pub lib/boot_log.dart test/boot_log_test.dart` (no new issues).

**Rollback:** revert the `boot_log.dart` and test edits (no other file touched). Behaviour reverts to propagate-on-throw, which is harmless with the default printer.

## Task 2 — BootLog: stop the process-global 3000-line cap from silencing later sessions (F5)

**Problem:** `_emitted` and `_capNoticeSent` (L33-34, L114-121) are process-global and cleared only by the test-only `reset()`. Reproduced (r4): after 3005 lines there were 3001 outputs (3000 lines + one cap notice); a later two-line "second session" produced nothing while `event` lines still went through. `Workflow.workflow` calls `attachFile` again on each run (workflow.dart L1918) but never resets the counter, so a long first session (e.g. a large pacman install) or several relaunches leave later boots with events only, which is exactly the case this log exists for. Severity: medium. (Whether users relaunch several times per process is assumed, not measured.)

**Steps:**
1. In `attachFile` (L77-85) reset `_emitted = 0` and `_capNoticeSent = false`, and update the doc comment (L75-76) to say a new attach starts a new line budget. (Alternative if the owner prefers `attachFile` to stay pure: add a public `BootLog.beginSession()` that does the reset and call it at workflow.dart L1918; that touches workflow.dart. Pick one and record the decision in the commit message.)
2. Keep the cap semantics within a session unchanged (3000 lines, one notice, events never counted).
3. Tests (new group `BootLog sessions`): fill to the cap, observe one notice; call `attachFile` again; feed 2 lines; both are emitted and a later cap trip emits a second notice. Keep the existing flood test (L81) unchanged.

**Verification:** `flutter test --no-pub test/boot_log_test.dart`.

**Rollback:** revert the reset lines in `attachFile` (and the `beginSession` call site if the alternative was chosen).

## Task 3 — Logcat reliability under process death: confirm on a device, then decide (F8) [UNVERIFIED on device]

**Problem:** `_logcat` (L44) uses `debugPrint`, which defaults to `debugPrintThrottled` (unbounded `Queue<String>`, 12 KiB per second budget; SDK print.dart L49/L70/L87, read by the requester and critic). From source reading and arithmetic only (no device, no AOT run): about 300 KB of capped output (3000 x ~100 chars, an assumed average) would take roughly 25 s to drain, and queued lines would be lost if the process dies (signal 9, crash, OOM kill), so logcat could miss the final lines of a failed boot. The file mirror (`_toFile`) is synchronous and does not have this problem. Correction from the critic pass: stage 2's claim that BootLog "competes with a duplicate `debugPrint` of the same output" was wrong. The `PTY Output` `debugPrint` calls (workflow.dart L105, L145) are in `Util.execute`/`executeCapture`, which BootLog does not feed; only a shared global queue could cause contention, and concurrency is not established.

**Steps:**
1. Gate (needs a device, outside this plan's read-only audit): on a debuggable build, flood the `TermPty` with ~3000 lines, run `adb logcat -d | grep IntelNode` while timing, then `kill -9` the app mid-flood; compare logcat lines to `run-as <pkg> cat <dataPath>/boot.log`. Record numbers in the PR.
2. If lines are delayed/lost in logcat but present in the file: (a) at minimum, add a sentence to the class doc comment (L5-10) saying logcat lines may lag or be lost on process death and `boot.log` is the reliable record; (b) optionally change `_logcat` to an unthrottled `print` (check that 303-char lines are not truncated by logcat). No unit test can assert logcat behaviour; the printer is already injectable, so existing tests are unaffected.
3. If the gate shows no loss, close this finding with the measured numbers and make no code change.

**Verification:** step 1 on-device comparison; `flutter test --no-pub test/boot_log_test.dart` if code changed.

**Rollback:** revert the `_logcat` line and doc comment.

## Task 4 — BootLog: count UTF-8 bytes, not UTF-16 units, for rollover (F6)

**Problem:** `_fileBytes += line.length + 1;` at L143 counts UTF-16 code units. Reproduced (r3): 270-char CJK lines are 810 bytes, so with a 5000-byte cap rollover happened after 19 lines and the rolled file was 14,958 bytes (about 3x); emoji 2x; ASCII exact. Worst case the 512 KiB cap becomes about 1.5 MiB per file. The rollover check is `>` before the write (L138), so one extra line always overshoots by design. Severity: low (boot logs are mostly ASCII).

**Steps:**
1. Add `import 'dart:convert';` and replace L143 with `_fileBytes += utf8.encode(line).length + 1;`.
2. Test: with `maxFileBytes` small and CJK lines, assert rollover happens at the byte-based threshold and the `.1` file size is within one line of the cap.

**Verification:** `flutter test --no-pub test/boot_log_test.dart`.

**Rollback:** revert the import and the L143 line.

## Task 5 — BootLog: make the unterminated-line guard report what it dropped (F3)

**Problem:** `feed` L59-62: when the pending remainder exceeds `maxLineLength * 4`, it is emitted once (truncated to `maxLineLength` + `...`) and discarded. Reproduced (r4): `feed('t', 'x' * 5000)` emitted ONE 323-char line and `flush` emitted nothing, so 4,700 chars were lost with only a trailing `...` as signal. The on-screen xterm is unaffected. Severity: low.

**Steps:**
1. In the guard branch only (L59-62), make the emitted line say how many characters were cut, e.g. append ` [+N chars dropped]` after the `...`-truncated text, computed from `remainder.length - maxLineLength`. Do not change the ordinary-truncation path (L111-113) so the existing test at test/boot_log_test.dart L52-58 (`endsWith('...')`) stays green; if the marker must follow the ellipsis, the guard-branch line is a separate path and does not break it.
2. Test: `feed` a no-newline chunk well over `maxLineLength * 4` and assert the marker with the right count; assert 1200 chars is still held and 1201 is emitted (existing boundary behaviour).

**Verification:** `flutter test --no-pub test/boot_log_test.dart`.

**Rollback:** revert the guard-branch change.

## Task 6 — BootLog: tighten the ANSI regexes and enrich the file-disabled notice (F9, F2b)

**Problem:** (F9, reproduced r5, cosmetic) charset-select `ESC ( B` leaves `(B` in the line (`(Bhi`), a bare `ESC c` leaves `c`, and an unterminated OSC leaves `]0;...` (regex L39-42 only matches BEL/ST-terminated OSC). (F2b) The notice at L146 prints only `e.message`, not the path or `osError`, which makes a failed boot-log write harder to diagnose. Severity: low.

**Steps:**
1. Extend `_ansi` (L39-41) with charset selects (`\x1B[()*+][0-9A-Za-z]`) and the common bare two-char escapes (`\x1B[78=>cDEHMNO]`) while keeping the existing CSI/OSC alternatives; optionally strip an unterminated OSC at end of line. Keep stripping after per-tag reassembly (this ordering is a strength).
2. Change the notice at L146 to include `file.path` and `e.osError?.message` when present.
3. Tests: `ESC ( B hi` yields `hi`; `ESC c` yields clean text; split CSI across chunks still stripped (guards the strength); the disabled notice contains the path.

**Verification:** `flutter test --no-pub test/boot_log_test.dart`.

**Rollback:** revert the regex and notice edits.

## Strengths (what not to break)

- **ANSI/CR handling after reassembly** (L103-110 with `feed` buffering L48-57): stripping runs after a line is reassembled per tag, so split CSI/OSC sequences, CRLF and `\r` progress redraws come out clean (r5). Do not move stripping to per-chunk.
- **Unterminated-remainder guard** (L59-62): bounds `_pending` memory and scales with `maxLineLength`; the 1200/1201 boundary is verified. Task 5 adds a marker, it must not remove the bound.
- **Events bypass the line cap** (L72-73, L114-121): lifecycle messages survive a stream flood and are verified to go through after the cap trips.
- **File failure policy** (L134-147): one notice, file disabled, logcat continues; only `FileSystemException` is caught there and every file failure tried (directory-as-file, missing parent, rename onto non-empty dir, read-only, deleted mid-run) landed in it. Task 1 adds guards around it, not instead of it.
- **Size seeding and single rollover** (L77-85, L134-143): avoids a `stat` per write; an oversized pre-existing log rolls on the first write.
- **Injectable `printer` and `@visibleForTesting reset()`** (L20, L87-101): keeps tests isolated. Note the suite covers only happy-path cases today (see gaps).
